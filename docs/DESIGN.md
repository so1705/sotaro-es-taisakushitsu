# ES対策室 設計書（v0.1 / 2026-10-19）

自分史（経験DB）をもとに、企業ごとのリサーチと多面的な審査で、ESを作成・添削するシステム。
Claudeだけで動かす。有料版（Pro：Claude Code／Cowork）と無料版（Claude.aiのプロジェクト）の2つを作る。

## 1. 共通の部品（両方の版で同じものを使う）
| 部品 | 中身 |
|---|---|
| 知識 | `knowledge/es-pro/` 00 本質原則／01 設問の裏読み／02 業界別／03 落ちるES／04 一次情報 |
| 手順 | `.claude/skills/` に工程ごとのSKILL.mdを置く。Claude CodeとClaude.aiのどちらでも読める形式なので、**手順は1か所に書いて両方の版で使う** |
| 評価基準のテンプレート | 足切り＋A〜F（下の5章） |
| 入力フォーマット | 【ES依頼】（下の2章） |
| 経験DB | 自分史インタビューで作る `経験DB.md`。**インタビューはChatGPTでやる**（Claudeの使用量を節約するため）。指示は `interview/自分史インタビュアー_指示.md`。レベル1（必須の3エピソード）／レベル2（中級）／レベル3（最上級）／深掘りモード（経験DBとES作成中のメモを合わせて、浅いところだけ掘る）。質問は1回に6〜10問まとめて出し、本人はボイスメモの文字起こしで答える。完了の基準を満たすまでラリーを続け、レベル1でも基準は下げない。ChatGPTは個人アカウントでGPTを新しく作れなくなった（2026-08〜）ので、配布は指示文を貼る形にする。Claude側（ES作成・ラリー）は、最後に「経験DB追記メモ」（新しく出た事実・浅いと判定された箇所）を出す。数字は確定／概算／使用禁止で管理する。有料版は取り込むときにエピソードごとのファイルに分ける |

## 2. 入力フォーマット
```
【ES依頼】
■企業名：
■コース・職種：
■種類：インターン／本選考
■募集ページURL：

■設問（1問ずつ）
Q1：
字数：
Q1の書き方メモ（任意）：
Q2：
字数：
Q2の書き方メモ（任意）：

■使いたいエピソード（任意）：
■全体の書き方メモ（任意）：
■備考（説明会・OB訪問で聞いた話、知ってることなど）：
```
- 設問はテキストで貼るのを基本にする。スクショは予備。
- 氏名・大学名・連絡先は入れない。
- 必須欄（企業名・設問）が空のときだけ止まって聞く。それ以外は、v1を出すまで止まらない。

## 3. 工程（両方の版で共通）
1. **リサーチ**：網羅チェック → 根拠カード（4章）
1-2. **構造分析**（es-pro）：6つの層 → 構造の一文 → 求める要素 R1〜R5（`構造分析.md`）。仮説のRは狙い撃ちで確かめる（知識13。2026-10-20に追加：ESは、会社が欲しい人物の構造に本人の経験を当てはめる作業なので）
2. **評価基準**：R1〜R5 をD項目にして `評価基準.md` を作って固定する
3. **方針審査**：本人の書き方メモと、AIの方針を、どちらの案か伏せて比べる → 採用／補強して採用／一部採用／不採用
4. **診断と設計**（es-pro）：当てはめ表（R × 経験DB）→ 今の素材での見込みの点数 → エピソードを選ぶ（候補3つを比べる）→ **骨子を本人に見せて、方向を決めてもらう（ここだけ止まる）**。見込みが80点未満なら、骨子と同じメッセージで補強の質問（最大2〜3つ。「なし」でも進める）を出す。良いESは本人の意図とロジックから生まれるため（リクルートのESの分析から、2026-10-20に変更）
5. **執筆**：勝ち筋を変えた複数案を書く
6. **審査**（6章）→ **統合**：書き直し指示を「重み×不足の大きさ」の順に最大3つ → 書き直す → 変えた項目を再審査＋他の項目が下がっていないか確認
7. **v1 を出す**（選んだ理由・評価基準・出典を付ける）
8. **ラリー**（7章）
9. **蓄積**：提出版、本人の修正で出てきた新しい事実（→ 経験DB）、後で記録する通過・落選

## 4. リサーチ
**網羅チェックのカテゴリ**（該当がなければ「該当なし」と書いて次に進む）
1. 公式の求める人物像・行動指針・価値観
2. 募集ページ（インターンの内容・課題・期間・対象）
3. トップメッセージ・人事メッセージ
4. 社員インタビュー・社員のブログやnote
5. IR・統合報告書・中期経営計画（事業の柱・注力領域・課題）
6. ニュース・プレスリリース（直近1年）
7. 競合比較（同業他社のうち2〜3社の同じ情報）
8. 選考情報（ログインなしで見られる公開記事のみ）＋本人の備考
9. 業界の構造変化（これからの5〜10年の需要・規制・技術・競争。官公庁・業界団体の統計、報道、統合報告書の「リスクと機会」）

各カテゴリは、`knowledge/es-pro/13_構造分析と素材の診断.md` の6つの層（L1 業界の構造／L2 会社の戦略／L3 公式の人物像／L4 コースの仕事／L5 設問の意図／L6 通過者の傾向）を埋めるために調べる。**2段で調べる**：1段目は広く、全部のカテゴリで構造の地図を作る。2段目は狙い撃ちで、構造分析で「仮説」になった要素と、骨子で使う事実だけを深く確かめる。

**根拠カード**（1つの事実＝1枚）
```
[C-12] 主張：〇〇を重視している　（層：L3）
出典：URL（種類：公式／報道／社員の発信／体験記）
引用：「……」
効く評価項目：D2・B
```
**止める基準**：連続3件読んで新しい傾向が出なかったら、そのカテゴリは終わり。根拠が1件だけの傾向は「仮説」と表示する。
**重み**：公式 ＞ 報道 ＞ 社員の発信 ＞ 体験記・まとめ記事。
**禁止**：ログインが必要なサイトの自動取得。

## 5. 評価基準
- **足切り**：本人が承認していない新しい経験・数字がない（盛りは【盛り提案】として本人が決める。07）／設問に答えている／字数9割以上／他社名なし／誤字・話し言葉なし／短所に致命的な情報なし
- **A 人柄**（判断の分岐・難しさの構造・自分の貢献の切り出し）
- **B 熱意**（原体験×会社固有の手段・他社に差し替えたら成り立たないか）
- **C 可能性**（行動原理化・別の場面での再現・入社後の活躍場面）
- **D 企業固有**（構造分析の R1〜R5 をそのまま使う。A〜Cのどれに属するかを割り当てる）
- **E 本人性・深掘り耐性**
- **F 読みやすさ**（重みは小さい）
- 4段階（不足／ギリギリ／十分／突出）で、各段階に具体例を付ける。設問ごとに重みを変える（ガクチカ：A＞E＞C、自己PR：C＞A＞D、志望動機：B＞D＞C）。
- 1回作ったら変更禁止。本人が情報を足したときや、項目を外したときだけ次の版にして、全部の版を新しい基準で判定し直す。

## 6. 審査
| 層 | 中身 |
|---|---|
| 1 機械チェック | 字数・他社名・禁止表現・表記ゆれ（Pythonで動かす。AIは使わない） |
| 2 事実監査 | ESを主張の単位に分けて、経験DBと照らし合わせる → 根拠あり／推測／根拠なし |
| 3 項目審査 | A・B・C・D・E・Fの担当制。判定には本文からの引用を必須にする。Dは常に2体。Bは「ギリギリ」と「十分」の境目のときだけ2体目を呼ぶ |
| 4 全体の印象 | 業界ごとに3人のペルソナ（例：コンサル＝人事／マネージャー／パートナー）。項目審査と食い違ったら、評価基準の外の問題として扱う |
| 5 一貫性 | ES内の設問どうし、過去に他社へ出したESとの矛盾 |

## 7. ラリー
- 項目ごとに、どちらの版が良いかを比べる。順番を入れ替えて2回判定し、食い違ったら「同等」。字数をそろえて比べる。
- 同等なら、本人の版を採用する。
- 見せるのは、勝ち負けが動いた項目だけ。全項目は折りたたむ。v3（両方のいいところを合わせた版）を提案する。
- 素材が足りないときだけ、本人に質問する。

## 8. 有料版の構成（Claude Code／Cowork。リポジトリをクローンしたフォルダで使う）
```
.claude/agents/
  es-pro              監修（構造分析・素材の診断・型の選択・骨子・最終判定）
  researcher          リサーチ（広く：カテゴリを分けて3体を並列／狙い撃ち：仮説の要素と骨子で使う事実だけ）
  es-writer           執筆（勝ち筋ごとに並列）
  reviewer-hr         審査：人事の一次選考＋業界ペルソナ（2周目は前の版→今の版の順で比較）
  reviewer-items      審査：A・B・C・E（2周目は今の版→前の版の逆順で比較）
  reviewer-company    審査：企業固有のD項目・会社の記述の裏づけ
  reviewer-facts      審査：深掘り面接官＋事実と盛りの監査
  ai-slop-reviewer    審査：AIっぽさ専任（最後に「なし」まで繰り返す）
.claude/commands/     /es・/es-review・/rally・/deep-dive
.claude/skills/       es-create・es-review・es-rally・deep-dive（無料版と共通の手順）
knowledge/es-pro/     00〜13
経験DB/  企業/<企業名>/   利用者のデータ（Gitの管理外）
```
- 1社あたりの使用量の実測（キリン）：約200万トークン。「軽く」ならリサーチ2体・審査1周で約半分
- 2026-10-20 の検証（サイバーエージェント・丸紅）で決めた流れ：リサーチ → 構造分析（求める要素 R1〜R5）→ 評価基準 → 素材の診断と骨子（本人が方向を決める。80点未満なら補強の質問）→ 執筆 → 5体×2周（統合では、経験DBにない場面・根拠のない会社の事実・会社の言葉の引用を採用しない）→ AIっぽさの除去
- 使用量を、質を落とさずに減らす工夫：審査役には「審査パック」（使った根拠カードとエピソードだけ。中身は削らない）を渡し、根拠カードの全文は企業固有の審査役だけが読む／2周目は、会社・事実・AIっぽさの審査役に続きで頼む（読み直しをなくす）。比べる役（人事・項目）は、引きずらないように新しく起動する／リサーチ役の返事は、チェック表と固有の事実だけにする

## 9. 無料版の構成（Claude.ai、プロジェクト1つ）
無料版のメッセージ数の上限（5時間で十数〜数十通）に合わせて、1社を4〜5往復で仕上げる。
```
プロジェクト「ES対策室」
  指示：free/アップロード用/プロジェクトの指示.txt（係の決め方と、いつも守ること）
  資料：知識1_ESの考え方（00・01・03・04・05）
        知識2_型と業界（02・06・08〜11）
        知識3_文章の仕上げ（07・12）
        手順_作成と審査（無料版の進め方＋有料版と同じ手順書・役の定義）
        経験DB.md（本人）
        〇〇社.md（作る係が出したファイルを、本人が追加）

チャットA（作る係）【ES依頼】：1回目 リサーチ→関門→評価基準→骨子で止まる／2回目 執筆→v1→「〇〇社.md」
チャットB（審査する係）「〇〇社 審査」：1回目 5つの役を独立に→統合→v2／2回目 比較（順番を逆に2回）→完成版→AIっぽさの除去
チャットC ラリー／チャットD 深掘り
```
- 知識と手順は `scripts/build-free.py` で有料版のファイルから作る（中身を二重に持たない）。リリースの前に必ず実行する
- 作る係と審査する係を別のチャットにするのは、自分で書いた文章を自分で審査すると甘くなるため
- 無料版で失うもの：審査役が本当に独立していない（同じチャットで役を切り替える）、並列で調べられない、深く調べるほどメッセージ数を使う

## 10. 配布の仕方（最終形）
- このリポジトリをGitHubで公開する → マニュアル（ドキュメント）にURLと手順を書いて配る。
- 受け取った人は、マニュアルをClaudeに読ませる → Claudeが必要なものを入れ、設定が必要なところは本人に聞いて、初期設定まで進める。
- 流れ：ChatGPTで自分史（GPTのリンク）→ `経験DB.md` → Claudeに入れる → 【ES依頼】。

### 経験DBの育て方
- 初回はChatGPTで作る（自分史インタビュアー。人物設定＋線のロジック。レベル1〜3）。
- その後の追加は、すべてClaudeの中でやる。ES作成チャットは、チャットに追記メモを出さず、「深掘り候補」と新しく出た事実を、静かに記録する（無料版：プロジェクトのメモリ／有料版：`経験DB/_深掘り候補.md`）。
- 時間があるときに、深掘りチャット（`.claude/skills/deep-dive`）を開く。線の点検表を作り直す → 優先順に掘る → 記録する。無料版で追記がたまったら、経験DB.mdを丸ごと出して入れ替える。
- 線の考え方は `knowledge/es-pro/05_線の設計図.md`。

### 更新の配り方
- GitHubの `VERSION`・`CHANGELOG.md`・タグで版を管理する（手順は `docs/更新のしかた.md`）。
- 有料版：起動時のフック（`scripts/update-check.sh`）が、14日ごとに確認して自動で取り込む。利用者のデータ（経験DB/・企業/）はGitの管理から外しているので、取り込んでも消えない。
- 無料版：Claudeが2週間ごとにVERSIONを確認して、差し替えるファイルを案内する。
